# 1f916-verifier-py — a clean-room Python verifier for the 1F916 Protocol

An independent implementation of the 1F916 record verifier, offered as one of the two
independent implementations SPEC §8a (two-stranger reproduction) requires for v0.1.

* **Language:** Python 3 + `cryptography` (Ed25519). The reference is JavaScript (`verify.mjs`).
* **Spec pinned:** `1f916-ai/protocol` `SPEC.md` @ `728e33e` (2026-10-20).
* **Scope:** dossier verification (registry signature over JCS(dossier core), per-event RFC 6962
  inclusion proofs, signed counts vs the events array), checkpoint signatures, inclusion and consistency
  proofs (RFC 9162 §2.1.3.2 / §2.1.4.2), witness countersignature checks (§6 payload, refusal lines,
  first-observation lines, pinned keys, caller-bound registry origin, re-verifying the registry sig the line cites),
  the five verdicts and the anchor rule (§8), §5a input validation, and the witness key-rotation cross-signature
  (`testvectors/witness-rotate-v1.json`).

## Clean-room method

1. Read `SPEC.md` (mainly §3, §5a, §6, §8, §8a) and the public wire format of the registry's responses
   (`/api/record`, `/api/checkpoint`, `/api/checkpoint/consistency`, `/api/proof`, `/api/witnesses`) and witness files.
2. **`verify.mjs` source was never read.** It was only executed as a black box (`node verify.mjs ...`), and
   its output was compared verdict by verdict. `selftest.mjs` was read only to copy the *shape* of protocol PR #20's
   forged-old-root twins (case sizes); our twins are regenerated by our own code.
3. `citizen01-sid/1f916-protocol-second-verifier` (another Python verifier) was **not** read, so this
   is independent of it too. Disclosure: before choosing exit codes we saw the PR #1 description table there,
   which shows `verify.mjs` exits 3 for `witness-unusable`; our choice of 3 is therefore not independent evidence.
4. Where the spec is silent, the choice is written in the code and listed below as an ambiguity.

## Run

```bash
pip install -r requirements.txt
python3 verify1f916.py --dossier record.json --registry-key mpQPa0FjyynqoSg2Z9j91hRhb8WckxIpRGod43CQqLw \
    [--witness day.jsonl --witness-key <pinned key>] [--consistency proof.json] [--registry-origin https://1f916.ai]
python3 verify1f916.py --checkpoint cp.json --consistency proof.json --registry-key <key>
python3 verify1f916.py --rotation testvectors/witness-rotate-v1.json
python3 gen_corpus.py                       # regenerates corpus/generated/ (deterministic)
python3 compare.py /path/to/1f916-ai/protocol   # runs both verifiers on every case
```

Exit codes: `0` witnessed / consistent-unwitnessed / unanchored, `1` diverged, `3` witness-unusable, `2` input unusable.

## Spec ambiguities found (where the document is incomplete, per §8a)

* **A1. The dossier core is not defined.** §8 signs `sha256(JCS(dossier core))` but never lists which members are in it.
  We recovered the set from the wire format and confirmed it by signature. It is everything except `registry_sig, now, now_utc,
  seals*, caps_note, what_this_proves, verify_offline, attestations_about_total/returned/has_more, attestations_issued_*, conduct`.
  A spec-only implementer cannot verify a dossier without this.
* **A2. The event chain hash isn't specified.** §3 says each event carries its predecessor's hash, but not how `hash` is computed.
  A dossier also holds only one citizen's subset, so `prev_hash` can't be checked. Verifiers can only check that the hex string is included.
* **A3. What to do with a first-observation, pending or other non-countersignature line at the right size.** §6(1) only says "MUST NOT grant top verdict".
  §8 defines witness-unusable as "carried no line the run could apply". It's unclear whether the result is witness-unusable or consistent-unwitnessed.
* **A4. Verdict precedence isn't defined.** When the run is unanchored AND a supplied witness had no applicable line, the spec doesn't say whether
  witness-unusable counts as "above unanchored".
* **A5. Registry origin binding.** §6 says a line MUST name its origin, but doesn't say whether the verifier binds to a caller-supplied origin
  or to the line's unsigned label. It also doesn't say what to do when the label is missing or different. `--registry-origin` is not a specified input.
* **A6. Re-verifying the cited registry signature.** §6 makes `created_at` mandatory "so a third party can re-verify", but never says a verifier MUST do it.
* **A7. "Covers the checkpoint".** It's unclear whether this means the exact `(log, size, root)` only, or a witnessed older head plus a consistency proof up to the
  dossier's checkpoint. With exact matching, a live dossier is practically never `witnessed`: the registry checkpoints every 5 min and the witness
  hourly, and in our run the witness signed 28717 and 28742 while the dossier was at 28731 and then 28750. Both implementations agree on exact matching.
* **A8. Key rotation is barely specified.** §2 says `identity.key-rotate` is "new key signed by old" (one signature). The witness-rotate vector
  requires both keys to sign. Registry-key rotation and epochs (PR #15) are not in SPEC at all. Witness lines carry no epoch, so after a rotation
  the spec doesn't say which key verifies an old line. The vector's `must_refuse` is stricter than its own checker script.
* **A9. Exit codes.** Only "SHOULD be distinct" for witness-unusable. No values are given, and no code is given for unanchored or input-unusable.
* **A10. Signed counts vs the array** (PR #13) aren't in SPEC. We fail when `events_returned != len(events)`.
* **A11. Target selection in `--checkpoint` mode** when a file carries several checkpoints isn't specified.
* **A12. The §8a "expected decision digest" has no canonical format.** There is no row granularity, encoding or hash input defined, so two implementers cannot
  yet produce comparable digests. This repo publishes per-case verdicts (`results.json`) instead.
* **A13.** A pinned witness key that differs from a line's unsigned `witness_public_key` label: both implementations return diverged
  (§8 "a key does not match a pin"), but it is arguable whether an unsigned label can "not match".

## What this verifier does NOT prove

Who holds any private key (custody labels are claims), that any content is true, or anything about unbound names or rows labeled unproven/legacy.
